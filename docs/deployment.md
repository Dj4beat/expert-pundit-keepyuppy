## Publish from a normal Windows terminal

1. Open PowerShell at the project directory. Install Node.js, Git and GitHub CLI if needed; use the existing GitHub login (`gh auth status`).
2. Run `npm ci`, `npm run vendor:phaser`, `npm test`, `npm run lint`, and `npm run build`.
3. Install Playwright browsers (`npx playwright install --with-deps chromium webkit firefox`) and run `npm run test:browser`.
4. Run `powershell -ExecutionPolicy Bypass -File scripts/publish.ps1`.
5. The helper waits for the Actions result, reads the actual Pages URL, and verifies the served bundle contains the creator credit and link. The workflow runs tests, provisions the pinned Phaser distribution, builds and deploys `dist/`. Both portable editions are attached as build artifacts.
6. Verify the actual URL and complete the physical-device checklist in `validation.md` before calling this a finished release.

The publication helper stops if the destination repository or staging folder already exists. It never overwrites an existing repository. It creates its local Git repository in `output/github-pages-source` because this agent’s workspace `.git` is protected. No credentials are copied or saved into source. GitHub CLI uses the existing login.

For an existing reviewed repository, copy source there and push normally; enable Settings → Pages → GitHub Actions. The workflow is already configured for `main`.

## Subpaths and future domains

Vite uses `base: './'`. All asset and service-worker paths are relative to the deployed directory; neither the GitHub repository name nor a hostname is embedded in gameplay. The worker’s cache name includes its registration scope and a hash of all built content. It only handles GET requests inside its own scope.

To move to the future Expert Pundit site, serve the entire `dist/` directory at the desired HTTPS path and let the worker register there. No code change is required. Saves cannot automatically cross browser origins: export a backup at the old domain and import it at the new domain. Keep the old URL available during the transition.

## Offline acceptance

Serve the production output (`npm run preview`), not Vite development mode.

1. On a fresh browser profile, load the project subpath. Observe download counts and wait for “Ready offline.”
2. Cut network access halfway through a fresh download. Confirm the message says download paused and never ready. Restore access and retry; already cached entries should be reused.
3. After a complete download, close and reopen the browser offline. Check all legends, venues, fonts, settings, guide and gameplay.
4. Clear one content entry from Cache Storage and request a download while offline. The app must not claim complete readiness until the missing file is restored.
5. Deploy a changed build. Keep a game running in the previous build. Confirm there is no automatic mid-run refresh. Return to menus, open Settings, install the waiting update and verify the new manifest.
6. Repeat at `/expert-pundit-keepyuppy/` and a different test subpath. Confirm no requests point to root-level `/art`, `/assets` or `/sw.js`.

Browser caches can be evicted by the operating system. The next download check verifies presence again. The portable file avoids service-worker storage dependence by embedding its assets.

## Browser screenshots

It writes real browser captures to `docs/screenshots/` and guide screenshots to `public/guide/`. Rebuild afterward to include them in the offline manifest.
